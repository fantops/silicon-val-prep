Why should you care?

  • Every PS / ASG workload that runs "on the NPU" goes through this exact pipeline.
  • "It ran on CPU" bugs almost always trace back to one stage in this flow.
  • Perf tuning (first-inference latency, sustained TOPS) is a tile / scheduling decision, not an ORT one.
  • When a QNN SDK bumps (2.40 → 2.45), the thing that actually changes is op-builder surface + HMX kernel library.
Takeaway goal: by slide 33 you'll be able to name the exact file to open when something goes wrong, in any of the five layers from ORT to silicon.

Session lifecycle

What happens when you call Ort::Session session(env, model_path, opts);

  1. Model load — protobuf → Graph
  2. Graph transforms — L1 rule-based → L2 assignment-aware → L3 EP-specific (ConstantFold, MatMulAddFusion, QDQ…)
  3. EP registration — in the order the user supplied them. Order matters.
  4. Partitioning — GetCapability() per EP; accepted clusters fused
  5. Compile — vendor compilers run; artifacts cached if context-caching is on
  6. Kernel resolution — remaining nodes → CPU EP kernels
  7. SessionState freeze — allocation plan locked
  8. Ready — Run() reusable, fresh ExecutionFrame per call
Expensive step: compile. This is where "first inference takes 5 seconds" comes from. Caching the artifact is mandatory for production.

The IExecutionProvider contract

class IExecutionProvider {
  // 1. QUERY: which nodes can I run?
  virtual std::vector<std::unique_ptr<ComputeCapability>>
    GetCapability(const GraphViewer& graph,
                  const IKernelLookup& kernel_lookup) const;

  // 2. BUILD: produce an executable per fused sub-graph.
  virtual Status Compile(const std::vector<FusedNodeAndGraph>& fused_nodes,
                         std::vector<NodeComputeInfo>& node_compute_funcs);

  // 3. RUNTIME hooks (optional)
  virtual Status OnRunStart(const RunOptions&);
  virtual AllocatorPtr GetAllocator(OrtMemType) const;
};

Compile() returns 3 function pointers per fused node:

  • create_state_func — once; load model, bind tensors.
  • compute_func — every Run(); invoke vendor runtime.
  • release_state_func — at teardown.

What Run() actually does

Run(inputs, output_names):
  ExecutionFrame frame(session_state, inputs)
  for node in execution_plan:              // topological; EP-mixed
    if node.ep == CPU:
      kernel.Compute(OpKernelContext(frame, node))
    else:
      node_compute_info.compute_func(
        state  = node_compute_info.state,
        ctx    = OrtKernelContext(frame, node))
  return frame.ExtractOutputs(output_names)

For NPU EPs the compute_func is a thin adapter:

  1. Pull input tensors from ExecutionFrame (zero-copy if allocator matches).
  2. Bind them to vendor I/O structs (Qnn_Tensor_t / xrt::bo / ov::Tensor).
  3. Kick device execution — this is when silicon does work.
  4. Return outputs (in-place via shared memory, or memcpy out).

QNN Execution Provider internals

onnxruntime/core/providers/qnn/

GetCapability

  • Walks nodes, checks each against op builders in qnn/builder/opbuilder/.
  • Groups contiguous supported nodes into clusters.
  • Acquires HTP power config (mutable state inside a const method).

Compile

  • Builds a QnnModel by replaying ORT nodes through the QNN C API.
  • Fast path: if qnn_context_cache_enable=1 and a .onnx_ctx.qnn exists → QnnContext_createFromBinary. Skips op-by-op rebuild.
  • Uses rpcmem_library.cc for zero-copy shared memory with the DSP.

Runtime

QnnGraph_execute → FastRPC → Hexagon DSP → HVX/HMX crunches → signal → return.

Vitis AI Execution Provider internals

onnxruntime/core/providers/vitisai/

  • GetCapability delegates to vaip::compile_onnx_model_3 — checks op list + shape + quantization constraints from a config JSON.
  • Compile serializes the sub-graph to a temp .onnx file and hands it to xcompiler (out-of-proc) which emits an XCLBIN.
  • Runtime loads the XCLBIN via XRT, binds tensors via xrt::bo, and xrt::run posts work to the AIE array via the NPU's ARM microcontroller.
  • Caching: XCLBIN is cached on disk under the model's cache dir — same fast-path story as QNN.

OpenVINO Execution Provider internals

onnxruntime/core/providers/openvino/

  • Most "pluggable" of the three — OpenVINO Core has device plugins for NPU / GPU / CPU. device_type=NPU pins it.
  • GetCapability converts the sub-graph to ov::Model and asks the NPU plugin for op support.
  • Compile → ov::Core::compile_model(NPU, cfg) produces a blob of NPU micro-code.
  • Blob cache: ov_bin_manager.cc keys on (model hash, device, config) → import_model on hit.
  • Runtime: borrow ov::InferRequest from pool → copy inputs → infer() / start_async.

Key: a pre-compiled QNN context binary freezes stages 1–3. Runtime just loads + runs stages 4–5. This is why shipping models load in milliseconds.

Who does what

Scalar VLIW core

  • Pointer arithmetic, loop control (HW loops = 0 branch cost)
  • Predication (no branches, mask-based)
  • Kicks off HVX/HMX — their instructions issue from this pipeline
  • Programs and fires DMA descriptors

HVX — vector

  • 1024-bit SIMD: 128×INT8, 64×INT16/FP16, 32×INT32/FP32
  • 32 vreg V0..V31 · 4 pred Q0..Q3
  • VMPY / VADD / VRMPY / VSHUFF / VCMP / VCONV
  • Pre-/post-quantize, bias, ReLU, softmax vector part

HMX — matrix

  • One instruction = 64×64 INT8 MAC tile (tens of thousands of MACs)
  • Reads tiles from VTCM; drains accumulators back to VTCM
  • Weights pre-packed to HMX native layout at compile time
  • Convs lowered via on-the-fly im2col addressing

VTCM — the scratchpad

  • Software-managed SRAM, multi-banked → parallel HVX+HMX+LS access
  • No coherency, no misses — deterministic latency
  • Double-buffered: DMA fills tile N+1 while HMX eats tile N
  • Spill = 5–10× perf loss. Tile size is king.

Unfilled slots = NOP = wasted issue bandwidth. The compiler's #1 job is packing.

VLIW syntax — one packet

{ V0 = vmem(R1+#0)                // slot 0: load activation vector
  V1 = vmem(R1+#128)              // slot 1: load next vector
  V4.w += vrmpy(V2.ub, V3.ub)     // slot 2: HVX rolling multiply-accumulate
  R1 = add(R1, #256)  }           // slot 3: scalar — bump pointer
  • Braces { ... } = one packet, executed in lock-step.
  • .w, .ub = element type (word, unsigned byte).
  • vrmpy = rolling multiply-accumulate — the workhorse of quantized convolution inner loops.
  • All four instructions complete in the same cycle.

Levels 2 · 3 · 4 of parallelism

Level 2 — Hardware multi-threading

Up to 4–6 HW threads share the engines at cycle granularity. When thread A stalls on a VTCM bank conflict, thread B's packet issues in its place.

Level 3 — HMX + HVX + DMA concurrency

  • DMA prefetches tile N+1 from DDR → VTCM bank B
  • HMX crunches tile N from VTCM bank A → accumulators → bank C
  • HVX post-processes tile N−1 in bank C (requant, bias, ReLU) → output stage

All three engines firing every cycle — this is what the 45-TOPS peak assumes.

Level 4 — Graph-level pipelining

Layer K+1 starts consuming layer K's tiles as soon as they land in VTCM. For transformers, Q/K/V MatMuls often share weight-loading DMA.

End-to-end

One Conv2D, all the way down

The ONNX node we're tracing

Conv(
  input  : [1, 64, 56, 56] int8   scale=0.031 zp=-2
  weight : [128, 64, 3, 3] int8   per-channel scales
  bias   : [128] int32
  output : [1, 128, 56, 56] int8  scale=0.047 zp=-5
)

Device: Snapdragon X Elite · Hexagon v73 HTP

Goal: trace every stage from ORT session load to HMX instructions.

Steps A · B · C — compile time

A · Partition

QNN EP's GetCapability matches in qnn/builder/opbuilder/conv_op_builder.cc, claims the node into a ComputeCapability cluster.

B · Graph assembly

Compile() calls QnnGraph_addNode(Conv2D, quant_params, strides, padding).

C · HTP IR + tile plan

QnnGraph_finalize → libQnnHtp.so:

  • Conv2D → im2col + MatMul at tile 64×64×64
  • Weights pre-packed to HMX native layout
  • VTCM layout: 2× activation tiles + 2× weight tiles + 2× accum spill + scale tables (≈2 MB of the 8 MB budget)
  • Loop nest: { DMA(W), DMA(A), HMX.MAC, HVX.requant+bias+ReLU, DMA(store) }

Steps D · E · F — runtime

D · Kernel pick

Compiler picks conv_int8_64x64x64_relu_v73 from the HTP op library (hand-tuned HVX/HMX intrinsics, pre-built).

E · Context binary

A–D are serialized to a QNN .bin. PerceptiveShell IHV packages ship this pre-built.

F · Device run

  1. Host FastRPC's input ptrs (ION shared memory) to HTP.
  2. Firmware allocates VTCM per the plan, starts DMA of tile 0.
  3. Scalar core enters outer tile loop — each cycle packs: DMA kick + HMX MAC + HVX requant on previous tile.
  4. HMX pumps 64×64 INT8 MACs per tile-instruction → INT32 accumulators.
  5. Accumulators drain → HVX does (out_scale / in_scale / w_scale) requant + bias + ReLU + clip → VTCM.
  6. DMA writes output tile back to DDR shared buffer.
  7. Completion event → FastRPC wakes host → compute_func returns.
~80 µs wall-clock on v73 at this shape. >90% productive HMX if the plan is tuned.

Three things to remember

1. The partitioner is the one decision point that determines whether your model runs on NPU at all. GetCapability() — know it.
2. "NPU execution" = HMX + HVX + DMA cooperating on tiles in VTCM, issued as 4-wide VLIW packets. Three engines, one scheduler.
3. The compile step is expensive and deterministic — cache the context binary, always. First-inference latency disappears.

Backup · QNN C API we actually call

// 1. Context / backend bring-up
QnnBackend_create(config, &backend_handle);
QnnContext_create(backend_handle, device_handle, config, &context);

// 2. Graph construction (Compile path)
QnnGraph_create(context, name, config, &graph);
QnnGraph_addNode(graph, node_descriptor);     // one per ORT node
QnnGraph_finalize(graph, profile, signal);    // triggers tile-planning

// 2b. Fast path — load pre-compiled
QnnContext_createFromBinary(backend_handle, device, cfg,
                            bin_ptr, bin_size, &context, profile);

// 3. Execute (every Run)
QnnGraph_execute(graph,
                 inputs, n_in,
                 outputs, n_out,
                 profile, signal);

Backup · Profiling the NPU

  • ORT profiler — session_options.enable_profiling = true gives per-node JSON. Shows which nodes ran on which EP and per-node wall-time.
  • QNN profile — pass a profile handle to QnnGraph_execute. Reports per-op HTP cycle counts, VTCM residency, DMA stalls.
  • hexagon-profiler — low-level tool from the SDK; gives packet-level counters (HMX util, HVX util, bank conflicts).
  • QXDM / airbridge — system-wide trace on dev devices; shows FastRPC round-trip and HTP power state transitions.
