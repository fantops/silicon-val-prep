What Is an NPU?

NPU = Neural Processing Unit — a chip purpose-built for AI math (multiply-accumulate operations).

Analogy: A CPU is a calculator — it does one multiply per clock cycle. An NPU is a factory of calculators — it does thousands of multiplies every cycle, in parallel.
  • CPU: flexible, handles any code, but ~1 MAC/cycle per core
  • GPU: thousands of small cores, great for graphics & AI, but power-hungry
  • NPU: thousands of MACs in a fixed grid, extreme perf/watt for AI
MAC = Multiply-ACcumulate: the atomic operation of AI.
result += weight × input — neural networks do billions of these.

TOPS Explained

TOPS = Tera Operations Per Second — how many trillion multiply-accumulate operations the chip can do per second.

ChipTOPS (INT8)Analogy
CPU core~0.51 calculator
Intel NPU~11Small factory
AMD XDNA16–50Medium factory
Qualcomm HTP~45Large factory
TOPS is a theoretical peak. Real throughput depends on memory bandwidth, model shape, and how well the compiler tiles the work.

Layer 3: ComputeCore — The Engine Room

What It Does

  • ORT Wrapper — thin C++ layer that hides ONNX Runtime's complexity from feature code
  • Model file management — finds .onnx files, decrypts them if encrypted at rest
  • Target selection via InferenceTarget enum: 
    enum InferenceTarget {
  NPU,    // preferred — best perf/watt
  CPU,    // fallback
  GPU,    // rarely used for our models
  REMOTE  // cloud endpoint (future)
};
  • EP options injection — assembles the options dict (htp_performance_mode, vtcm_mb, etc.) based on target + platform

Session Lifecycle

// Simplified flow
ComputeCoreSession* CreateComputeCoreSession(
    const char* modelPath,
    InferenceTarget target)
{
  // 1. Decrypt model if needed
  auto bytes = DecryptModel(modelPath);
  // 2. Build ORT SessionOptions
  auto opts = BuildOptions(target);
  // 3. Create ORT InferenceSession
  //    → triggers EP compile on first call
  auto session = new Ort::Session(env,
      bytes.data(), bytes.size(), opts);
  return Wrap(session);
}
Key detail: The ORT session is created once and reused for every inference call. Creating it is expensive (model compile); running it is cheap.

Layer 4: ONNX Runtime — The Brain

ORT's 6-step session-creation pipeline (this is where all the magic happens):

StepWhat HappensPlain English
1. LoadDeserialize protobuf → in-memory graphRead the .onnx file into a data structure of nodes (operations) and edges (tensors)
2. Graph TransformsConstant folding, QDQ node fusion, layout transforms (NCHW↔NHWC)Simplify the graph: merge adjacent operations, pre-compute constants, reformat data layouts
3. PartitioningEach EP's GetCapability() claims nodes it can runAsk the NPU plugin "which operations can you handle?" — unclaimed nodes stay on CPU
4. CompileEP's Compile() → produces context binaryThe NPU compiler turns claimed nodes into a hardware-specific binary blob (cached for next launch)
5. Kernel ResolutionRemaining CPU nodes get kernel implementationsFor anything the NPU can't do, find CPU code that can
6. Session FreezeAllocate buffers, finalize execution planLock everything in place — session is ready to run
QDQ Fusion — QDQ = Quantize-DeQuantize nodes. ORT fuses them: instead of DQ→Conv→Q (float math), fuse to QConv (INT8 math done entirely on NPU).
Context binary cache: Steps 1–4 are slow (seconds). Once cached, the binary is loaded directly at step 4 = sub-second startup. Set ep.context_enable=1 + ep.context_file_path.

Pipeline: While DMA fetches tile N+1 into VTCM buffer A, HMX crunches tile N from VTCM buffer B, and HVX post-processes tile N-1's output. All three engines are always busy.
  • DMA moves weights & activations from DDR → VTCM (or VTCM → DDR)
  • HMX does the heavy INT8 matrix multiplies (convolutions, matmuls)
  • HVX handles activation functions (ReLU, sigmoid), element-wise adds, requantization
Why this matters: If any engine stalls (e.g., DMA can't fetch fast enough from DDR), the whole pipeline bubbles. This is why VTCM size matters — more VTCM = bigger tiles = fewer DDR round-trips = fewer stalls.
The real bottleneck is memory bandwidth, not compute. HMX can crunch 45 TOPS, but DDR can only deliver ~60 GB/s. For bandwidth-bound layers (1×1 convs, depthwise), actual throughput is far below 45 TOPS.

FP32 → INT8 Quantization — Why & How

The Formula

Quantize:   q = round(x / scale) + zero_point
Dequantize: x ≈ (q - zero_point) × scale

Worked example (scale=0.005, zero_point=150):
  FP32 value:  0.75
  Quantized:   round(0.75 / 0.005) + 150 = 150 + 150 = … 
               wait — round(150) + 150 = 300? No:
  
  q = round(0.75 / 0.005) + 0 = 150  (zero_point=0)
  Dequantized: 150 × 0.005 = 0.750 ✓

  But if zero_point=1:
  q = round(0.75 / 0.005) + 1 = 151
  Dequantized: (151 - 1) × 0.005 = 0.750 ✓

  Precision loss example (scale=0.01):
  q = round(0.75 / 0.01) + 0 = 75
  Dequantized: 75 × 0.01 = 0.750 ✓  (lucky)
  
  q = round(0.743 / 0.01) = 74
  Dequantized: 74 × 0.01 = 0.740 ≠ 0.743  ← lost!

Why INT8?

4096× more MACs on HMX. FP32 uses one MAC unit per multiply. INT8 packs 4 values in the same bits → HMX's 64×64 array does 4096 INT8 MACs per instruction vs ~1 FP32.

Danger Zones

  • Softmax — exponentials amplify tiny INT8 rounding errors
  • LayerNorm — variance computation is numerically sensitive
  • First & last layers — input distribution is wide, INT8 range too narrow
Mixed precision: INT8 for compute (convolutions, matmuls) + FP16 for accumulators (running sums) + FP16 for sensitive layers. Set enable_htp_fp16_precision=1 in QNN EP options.
Per-channel vs per-tensor: Per-channel = different scale per output channel (more accurate, larger model). Per-tensor = one scale for whole tensor (smaller, less accurate).

Bug #1: Vitis AI Memory Leak

Symptom

Memory grows continuously during model compilation on AMD. Never freed. Eventually OOM.

Debug Journey

  1. WPA (Windows Performance Analyzer) — staircase pattern in heap graph. Memory only goes up, never down.
  2. AppVerifier — enabled heap tracking. Confirmed: allocations in onnxruntime_vitisai_ep.dll never freed.
  3. WinDbg — attached debugger, set breakpoints on alloc/free.
  4. Stack trace — leak traced to ORT's internal API used by Vitis EP.

Root Cause

Found in ORT source: global_api.cc line 637, function attr_proto_release_string:

// BUGGY — sets pointer to null,
// but never frees the string memory!
void attr_proto_release_string(
    OrtApiBase* api,
    ONNX_NAMESPACE::AttributeProto* attr)
{
  std::string* pstr = attr->release_s();
  pstr = nullptr;  // ← BUG: leak!
  // Should be: delete pstr;
}
// FIX
void attr_proto_release_string(...) {
  std::string* pstr = attr->release_s();
  delete pstr;     // ← actually free it
}
Lesson: EP bugs often live in ORT's internal API layer, not in the EP itself. Attach ORT source to debug EP issues.

Bug #2: Root Cause — The Exact Function

File: qnn_backend_manager.cc → CreateContextFromListAsync(), lines 1049–1061.

ORT 1.23 — load one, free one

for (auto& it : context_bin_map) {
  // Allocate buffer for ONE context binary
  auto buffer = std::make_unique<char[]>(size);
  ReadContextBin(path, buffer.get());

  // Create context from this buffer
  CreateContextFromBinary(buffer.get(), size);

  // buffer freed HERE (unique_ptr scope ends)
  // Only ~1 context in memory at any time
}
Peak memory: ~1 context binary (~tens of MB). Load it, use it, free it. Next one reuses the same memory.

ORT 1.24 — accumulate ALL, then create

// NEW: vector holds ALL context binaries at once
std::vector<std::vector<char>> buffer_list;

for (auto& it : context_bin_map) {
  std::vector<char> buffer;
  ReadContextBinIfValid(path, buffer);

  // Buffer KEPT ALIVE in buffer_list
  buffer_list.push_back(std::move(buffer));
}
// All buffers in memory simultaneously
// → 102K demand-zero page faults (~400 MB)
Peak memory: ALL context binaries at once. For N contexts × ~tens of MB each → hundreds of MB touched simultaneously → 59× page fault spike.
Why it was changed: The async context creation path needs all buffers alive simultaneously so multiple contexts can be created in parallel — needed for concurrent model loading (MEP/ConcurrencyTestSuite). But for single-model inference (our PSMU case), it's unnecessary overhead. Secondary cause: commit 3a1bb09 added reserve() for VTCM sharing pointer stability, compounding the spike.

Bug #3: Accuracy Divergence Across Platforms

Same .onnx model, three NPU platforms, three different numerical outputs.

Why it happens

  1. Different partitioning. QNN claims 47/50 nodes, OpenVINO 38, Vitis 30. More CPU fallback = more boundary crossings = more rounding error.
  2. Vitis cluster-level rejection. One unsupported op dumps the entire subgraph to CPU (vs per-op on QNN/OV).
  3. Different rounding. INT32→INT8 requantization uses implementation-defined rounding. Tiny diffs compound over layers.
  4. Different QDQ fusion. QNN fuses aggressively. OV may split differently. Changes the precision path.

Debug approach

  1. CPU EP = golden reference. Run on CPU first. If correct → problem is in EP, not model.
  2. Compare node claims. log_severity_level=0, grep "nodes supported" per platform.
  3. Dump + diff graphs. session.save_optimized_model_path → open in Netron → diff QDQ patterns.
  4. Per-node output comparison. Find exact layer where outputs diverge.

Fixes

  • models_caches: ["qnn;ov;vitis"] — separate cached binaries per platform
  • OrtEpValidation workload — automated cross-EP accuracy test
  • enable_htp_fp16_precision=1 — FP16 on sensitive layers
  • PS Eval pipeline — per-API metrics (PSNR, WER, BLEU)
Golden rule: CPU EP correct + NPU EP wrong → bug is in quantization/EP handling. Diff the partitioned graphs.

Bug #4: Paint + Camera NPU Concurrency (Part 1)

Symptom

  • Camera preview drops frames when Paint SR is running
  • Not always reproducible — depends on timing
  • Only happens on NPU (GPU path works fine)

Root Cause

NPU has a single hardware scheduler with no preemption.
Unlike GPUs (which can preempt mid-kernel), the NPU runs one graph to completion before starting the next. If SR submits 36 tiles, Camera waits for all 36.

The Semaphore Repro

Wrote a C test exe to guarantee 100% reproduction:

HANDLE sem = CreateSemaphore(NULL, 0, 2, NULL);

// Thread A — Paint SR workload
DWORD WINAPI SrThread(LPVOID) {
  WaitForSingleObject(sem, INFINITE);
  for (int tile = 0; tile < 36; tile++)
    ComputeInference(srSession, tileData[tile]);
  return 0;
}

// Thread B — Camera workload
DWORD WINAPI CamThread(LPVOID) {
  WaitForSingleObject(sem, INFINITE);
  for (int f = 0; f < 30; f++) {
    LARGE_INTEGER t0; QueryPerformanceCounter(&t0);
    ComputeInference(camSession, frame[f]);
    LARGE_INTEGER t1; QueryPerformanceCounter(&t1);
    if (elapsed(t0,t1) > 33ms) log("DROPPED");
  }
  return 0;
}

// Main — release both threads simultaneously
ReleaseSemaphore(sem, 2, NULL); // → BOOM
Key insight: The semaphore ensures both threads start NPU submission at exactly the same instant — no timing luck needed. 100% repro rate.

3Camera frame 0 queued, waiting
6–105SR tiles 1–35 run back-to-back
108Camera frame 0 finally starts
Camera frame 0 waited 108 ms — that's 3.2 frame periods at 30fps. User sees visible stutter.

Mitigations

  1. Throttle submission — SR submits tiles in batches of 4 with Sleep(1) gaps, letting Camera interleave
  2. MEP scheduler priority classes — tag Camera as HIGH, SR as LOW. Scheduler drains high-priority first.
  3. QNN hints — set htp_performance_mode=balanced for SR (slower but yields more) vs burst for Camera
  4. IHV firmware preemption — requested from Qualcomm. Future firmware may support mid-graph preemption.
Fundamental NPU limitation. GPUs solved this decades ago with hardware preemption. NPU firmware doesn't support it yet. Until IHVs add preemption, software scheduling is our only tool.

SR vs Mu — Two Very Different Workloads

Super Resolution (SR)

  • 1 model (single ONNX file)
  • 1 call per tile — input tile in, upscaled tile out
  • No state — each tile is independent, order doesn't matter
  • Stateless — no memory of previous tiles
  • Parallelizable: could run tiles on multiple NPUs

Mu (Language Model)

  • 3 models:
    • Embedder — runs on CPU (converts token IDs → vectors)
    • Encoder — runs on NPU (processes full input sequence once)
    • Decoder — runs on NPU (generates one token per call)
  • Autoregressive — each token depends on all previous tokens
  • KV cache grows — every generated token adds to memory

Why Mu is harder than SR:
  • Can't parallelize — token N depends on token N-1
  • KV cache grows linearly — memory pressure increases
  • Latency per token matters — user sees each token stream in

Summary — Three Things to Remember

1. Six Layers, One Path
Every AI inference — SR, Mu, any model — flows through: App → PS API → ComputeCore → ORT → EP → NPU. Understanding this stack is the key to debugging any model issue.
2. Context Binary = Fast Path
First run compiles the model (slow, seconds). Subsequent runs load the cached context binary (fast, milliseconds). ep.context_enable=1 is critical for production.
3. Three NPUs, Different Tradeoffs
Qualcomm wins raw throughput thanks to 8 MB VTCM + HMX density. Intel wins ecosystem compatibility. AMD wins scalability. The real bottleneck is always memory bandwidth, not compute TOPS.
